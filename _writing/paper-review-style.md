# 논문 리뷰 블로그 작성 기준

이 블로그의 글은 논문을 다시 읽을 때 작성자가 자신의 이해를 복원할 수 있어야 한다. 결론만 요약하는 대신, 기존 방법의 문제에서 제안 방법의 설계와 실험 근거까지 이어지는 사고 과정을 남긴다. 한국어 설명에 익숙한 영어 기술 용어와 수식을 섞고, 이해가 막히는 부분에는 원문보다 많은 설명을 배분한다.

사용자가 2026년 10월 12일 요청한 지속적 작성 기준이다. 전체 39편의 형식을 조사하고 최신 7편을 원문과 대조하여 도출했다. 근거와 예외는 [원문 대조 분석](paper-review-analysis.md), 조사 대상은 [포스팅 목록](paper-review-inventory.md)에 있다. **내용에 대응하는 문법·제목 계층·수식 기호 목록·토글·들여쓰기·빈 줄은 [Markdown 작성 명세](paper-review-markdown-format.md)를 반드시 함께 적용한다.** 아래 기준을 기본값으로 적용하되 현재 사용자의 구체적 요청을 우선한다.

## 글의 목적과 독자

- 대상 독자는 이 논문을 이해하고 나중에 다시 찾아볼 작성자 자신이다. 일반 대중을 위한 홍보성 소개나 학술 초록의 번역으로 쓰지 않는다.
- Transformer, CLIP, diffusion 등의 이름은 익숙하게 사용할 수 있다. 그러나 현재 논문의 작동을 이해하는 데 필요한 개념·기호·변형은 다시 설명한다.
- “왜 필요한가”, “어느 representation을 바꾸는가”, “어떤 정보가 남거나 사라지는가”, “학습 신호가 어디로 전달되는가”에 먼저 답한다.
- 생성 모델과 멀티모달 모델, representation alignment, 정보 병목, 시각 세부·공간 관계, 모델 재사용과 효율성은 반복적으로 깊게 다루는 관심사다. 해당 논문과 관련 있을 때 설명의 연결점으로 활용한다.
- 기존 글을 근거로 실제 학력·수학 숙련도·구현 경험을 단정하지 않는다. 연구 경험을 새로 만들어 1인칭으로 쓰지 않는다.

## 원문을 글로 바꾸는 순서

1. 논문 링크의 제목·저자·버전을 확인하고 원문 전체 본문을 먼저 읽는다. 핵심 수식, 방법 그림, 주요 표, ablation과 limitations를 확인한다.
2. 핵심 방법을 이해하거나 포스팅이 인용하는 주장에 필요한 appendix·supplement를 읽는다. 관련 연구를 더 설명해야 하면 해당 1차 출처도 확인한다.
3. 내부 작업 메모에 `원문 위치 → 남길 주장 → 추가 설명 → 사용할 그림·표 → 조건·예외`를 기록한다. 이 작업 메모를 포스팅에 그대로 붙이지 않는다.
4. 이 논문만의 학습 질문을 정한다. 예: 어떤 단계에서 시각 정보가 손실되는가, next-scale이 무엇을 바꾸는가, loss가 왜 메모리 절약으로 이어지는가.
5. 독자가 이 질문에 답할 수 있는 순서로 Background와 방법 설명을 구성한다. 논문 절 순서를 참고하되 이해에 필요한 재배치는 허용한다.
6. 실험을 방법의 주장과 연결하고, 중요한 결과와 예외를 남긴다. 결론은 방법의 핵심과 성립 범위를 회수한다.
7. 원문과 대조하여 숫자·단위·부호·차원·학습 범위·평가 조건·링크·그림 대응을 검수한다.

논문을 구하지 못하면 읽지 않은 내용을 아는 것처럼 작성하지 않는다. 확인 가능한 범위를 밝히고 미확인 결과를 확정하지 않는다. 논문 링크가 잘못되었다면 제목과 저자에 맞는 공식 원문을 찾아 사용한다.

## 정보 선택 기준

| 구분 | 작성 기준 |
| --- | --- |
| 반드시 남길 정보 | 기존 방법의 구체적인 실패, 연구 질문, 목표와 기여, 새 설계의 차이, 핵심 수식·알고리즘, 학습·추론 경로, 주요 실험 조건과 결과, ablation, 주장에 영향을 주는 예외와 한계 |
| 이해를 위해 추가할 정보 | 필요한 배경 정의, 모듈의 역할, 기호·차원·값의 범위, 수식의 중간 변형, gradient와 freeze의 관계, 단계별 입력·출력, 기존 방법과의 비교, 작은 예시·의사코드 |
| 더 자세히 설명할 정보 | 새 방법의 핵심 novelty, 직관만으로 오해하기 쉬운 수식, 학습 신호·representation이 이동하는 경로, 실패한 단순 대안에서 최종 설계로 이어지는 논리, 중요한 ablation의 해석 |
| 압축해도 되는 정보 | 방법을 이해하는 데 영향을 주지 않는 선행연구 나열, 모든 baseline의 모든 숫자, 반복적인 qualitative 예시, 통상적인 optimizer 설정의 긴 나열, 주변적인 부록 세부사항 |
| 압축하면 안 되는 조건 | paired data의 사용 단계, pretrained 지식의 출처, teacher와 trainable 모듈의 구분, 평가 데이터·해상도·sampling·rejection 조건, 추가 연산 비용, 점수의 단위, 실패하거나 덜 좋은 결과 |

관련 연구는 이름 목록으로 끝내지 않는다. 어떤 문제를 어떤 단계에서 해결하는 계열인지 묶고, 이 논문이 어디에 위치하는지 설명한다. 비용·데이터 효율이 핵심 주장이라면 실제 학습·추론 비용과 pretrained 비용 포함 여부도 남긴다.

## 기본 구성

최근 글의 공통 흐름은 다음과 같다. 모든 논문에 똑같은 목차를 강제로 적용하지 않는다.

1. Jekyll front matter
2. `# **[논문 리뷰] 영문 논문 제목**`
3. 인용문 형태의 논문 정보와 링크
4. `## **Background**`
5. `## **Introduction**`와 Goal, Motivation, Contributions
6. 필요에 따라 Related Work 또는 Preliminaries
7. Method 또는 핵심 방법의 이름을 사용한 장
8. Experiments 또는 Empirical Results
9. Conclusion과 필요한 Limitations
10. 실제 필요가 있을 때 질문, 비교, 코드 해설

RF/flow처럼 유도가 중심이면 SD3처럼 방법을 여러 최상위 장으로 나눈다. 분석 논문이면 질문별 관찰과 실험을 따라간다. 새로운 pipeline이면 전체 그림을 먼저 보여주고 단계별로 분해한다. 용어 설명이 짧으면 Background와 Preliminaries를 합치고, 같은 설명을 중복 복사하지 않는다.

### Background

- 독자가 방법을 이해하기 직전에 필요로 하는 개념만 선정한다.
- `개념 정의 → 일반적인 구조나 수식 → 이 논문에서 필요한 이유`로 연결한다.
- 관련 개념이 이미 등장한 글이 있으면 적절히 내부 링크를 붙인다. 해당 용어를 현재 문맥에서 짧게 다시 설명한다.
- ML 전체를 처음부터 설명하지 않는다. 반대로 어려운 용어를 이름만 제시하고 넘어가지 않는다.
- 일반 VAE와 VLV autoencoder, 입력 CLIP encoder와 teacher VFM처럼 이름이 비슷한 다른 구성요소를 구별한다.

### Introduction

먼저 기존 방식의 병목과 제안 아이디어를 연결한 설명을 쓴다. 그다음 목적, 동기, 기여를 분리한다.

- **Goal**: 해결하려는 문제와 최종 task
- **Motivation**: 기존 방법이 실패하는 이유와 새로운 접근이 필요한 근거
- **Contributions**: 무엇을 새로 정의·설계·검증했는지

여기에 핵심 개념도나 대표 결과 그림을 둘 수 있다. 성능을 소개할 때는 논문 발표 시점과 실험 범위를 유지하고, 현재의 모든 모델에 대한 SOTA라고 확대하지 않는다.

### Method

전체 구조를 설명한 뒤 학습 단계, 모듈, 추론 순서로 펼친다. 각 핵심 구성요소는 다음 내용을 갖춘다.

- 해결할 문제와 설계 이유
- 입력과 출력, representation이 속한 공간
- 구체적인 연산 또는 알고리즘
- 핵심 수식과 기호 설명
- 원문이 생략한 연결 단계나 직관
- 이 연산이 뒤의 학습·추론 또는 실험과 연결되는 방식

**학습과 추론을 따로 설명한다.** 데이터 사용 범위, trainable 모듈, frozen 모듈, loss 적용 대상, gradient가 흐르는 경로를 구분한다. frozen 모듈은 가중치를 업데이트하지 않는다는 의미이며, 입력까지의 미분을 자동으로 차단한다는 의미가 아니다.

모듈은 이름 목록으로 끝내지 않는다. 예를 들어 projector라면 어느 공간에서 어느 공간으로 바꾸는지, 어떤 차원을 맞추는지, 출력이 어떤 토큰으로 쓰이는지 설명한다. 여러 projector가 있으면 역할과 기호를 분리한다.

VIRAL처럼 논문이 진단 실험과 실패한 단순 대안을 거쳐 방법에 도달하면 그 흐름을 유지한다. 성능이 낮았던 대안도 새 방법이 필요한 이유를 설명하므로 남긴다.

### 수식 설명

기본 단위는 `식이 필요한 이유 → 수식 → 기호 정의 → 연산의 의미 → 설계상의 효과`다.

- inline math는 `$...$`, display math는 `$$...$$`를 사용한다.
- display math의 여는 `$$`와 닫는 `$$`는 각각 독립 행에 둔다. `\[...\]`와 `\(...\)`로 대체하지 않는다.
- 원문 대응이 필요한 주요 식에는 `\tag{...}`를 사용할 수 있다. 추가 유도식에 원문 번호를 잘못 붙이지 않는다.
- 중요하거나 새로 도입한 기호는 해당 식 또는 연속된 식 묶음 바로 아래에 `- $기호$: 설명` 목록으로 정의한다. 필요하면 shape, 분포, 범위, 초기값을 함께 적는다.
- loss의 각 항이 무엇을 늘리거나 줄이는지, 실제로 어떤 파라미터가 업데이트되는지 적는다.
- 식 변형은 “즉 같다”로 건너뛰지 않고 대입·미분·기댓값 전개·상수 제거 등 필요한 단계를 보인다.
- 긴 증명은 접을 수 있어도 최종 식의 의미와 적용 조건은 본문에 남긴다.
- 조건부 목표와 주변 목표, 표본 경로와 학습된 생성 경로, log-temperature와 temperature, latent와 conditioning embedding을 섞지 않는다.
- 수학적 해설이 원문보다 확대되면 성립 조건을 확인한다. 복잡도와 속도는 별개이며 KV cache, token grid 크기, 구현 가정도 고려한다.

### Experiments

결과 표를 보여주기 전에 실험이 확인하려는 질문을 적는다. 그다음 설정, 결과, 해석을 이어간다.

1. **목적**: 방법의 어떤 주장을 확인하는가
2. **설정**: task, 데이터, baseline, 바뀐 변수와 고정한 조건
3. **지표**: 무엇을 측정하고 큰 값 또는 작은 값 중 어느 쪽이 좋은가
4. **결과**: 핵심 수치나 추세와 중요한 예외
5. **해석**: 어떤 설계가 왜 필요한지, 무엇까지 뒷받침하는지

VLV처럼 서로 다른 평가 경로가 있으면 직접 embedding reconstruction, caption으로 T2I reconstruction, 사람·VLM 평가, text-only VQA를 구분한다. 한 평가 지표가 전체 task 성능을 대표한다고 쓰지 않는다.

Ablation은 구성요소별로 나누고 “이 항을 넣으면 점수가 올랐다”에서 끝내지 않는다. 어떤 가설을 검증했는지와 기본 설정을 선택한 이유를 설명한다. 정성 결과는 그림의 위치·색·영역·질문과 응답 차이를 실제로 읽어준다.

실험별 제목은 원문의 영어 제목을 유지하거나, 이해에 도움이 되는 한국어 설명을 덧붙인다. `목적/설정/결과` 소제목을 매번 기계적으로 반복할 필요는 없다.

### Conclusion과 추가 해설

- 문제, 핵심 설계, 확인된 결과, 적용 범위를 회수한다. 새 주장을 갑자기 추가하지 않는다.
- 구현 비용, teacher의 한계, 데이터 편향, 현재 지원하지 않는 task 등 논문의 결론을 해석하는 데 필요한 제약을 남긴다.
- 원문이 밝힌 한계와 글에서 추가한 판단을 구분한다. 추가 판단은 “이 구조에서는 …을 고려해야 한다”와 같이 근거·범위를 보인다.
- 실제 질문이 있으면 `쓰면서 생긴 Question` 같은 추가 장에서 비교하거나 풀어쓴다. 관련 논문을 읽어 사실을 확인하고 답하지 못한 부분은 미해결 상태로 남긴다.
- 개인적 느낌이나 연구 경험은 사용자가 제공한 것만 1인칭으로 서술한다. 기술적 관심사만으로 감정·경험을 만들어내지 않는다.

## 문체와 호흡

- 한국어 평서문을 기본으로 한다. `~이다`, `~한다`, `~의미한다`, `~볼 수 있다`, `~시사한다`가 주된 어미다.
- `embedding`, `feature`, `token`, `latent`, `backbone`, `projector`, `loss`, `sampling`, `fine-tuning`, `zero-shot` 등 익숙한 영어 용어를 자연스럽게 섞는다. 문서 안에서는 같은 대상을 같은 용어로 부른다.
- 추상적 설명 직후 `즉`, `다시 말해`, `쉽게 말해`, `예를 들어`, `때문에`, `따라서`로 해석이나 예시를 연결한다. 뜻이 같은 요약을 반복해 분량을 늘리지 않는다.
- 한 문단은 대체로 하나의 설명 단계에 집중한다. 최근 표본의 일반 설명 문단 중앙값은 글별 약 67~103자였지만 이를 글자 수 규칙으로 강제하지 않는다.
- 핵심 개념·설계 차이·중요 결과는 **굵게** 강조한다. 문장 전체를 상시 굵게 만들지는 않는다.
- 순서가 있는 과정에는 번호 목록, 병렬적인 역할·조건에는 bullet, 짧은 보충 해설에는 인용문을 사용한다.
- 긴 부연 유도·상세 비교·질문 답변은 관련 본문 옆의 HTML 토글에 접어 둔다. 소절을 나누는 H3와 부연을 접는 details의 역할을 구별한다.
- 인용문은 서지정보뿐 아니라 직관·주의점·짧은 예시에도 쓰인다. 직접 인용이 아니라면 저자의 원문 발언처럼 꾸미지 않는다.
- 설명 중심의 담백한 문체를 따른다. `혁신적`, `압도적`, `근본적으로 해결`, `완벽히 보장` 같은 수식어를 근거 없이 사용하지 않는다.
- 본문에 영어 문장을 장문으로 복사하거나 초록을 그대로 번역해 붙이지 않는다.

## 그림과 표 편집

- 방법의 전체 그림을 제시한 후, 복잡한 그림의 부분을 잘라 해당 단계 설명 바로 옆에 배치할 수 있다. Diffusion Bridge의 학습·decoder·추론 분리와 SD3의 image/text/MM-DiT block 분해가 대표적이다.
- 원문의 그림·표는 설명의 증거다. 넣은 모든 그림에는 무엇을 봐야 하는지와 해당 문단의 결론을 연결한다.
- 그래프는 축, 조건, 색·범례, 증가·감소 방향과 예외를 확인한다. 여러 패널은 각각 무엇을 비교하는지 설명한다.
- 원문 표의 모든 숫자를 본문에 옮길 필요는 없다. 중요한 비교, 대표 수치, 결과를 바꾸는 조건과 반례는 텍스트로 남긴다.
- 직접 읽은 PDF의 figure/table 번호와 페이지를 작업 중 기록한다. 이미지 파일명만으로 내용을 추정하지 않는다.
- 최근 표본은 Markdown 이미지와 HTML `<img>`를 함께 사용한다. 이미지 폭 조절과 가로 비교 배치는 가독성이 필요한 경우에만 쓴다.
- 이미지가 필요하면 원문에서 적절히 추출해 로컬 assets에 둔다. 존재하지 않는 경로나 불필요한 placeholder를 완료된 이미지처럼 남기지 않는다.
- 논문을 제공받아 리뷰를 작성할 때는 필요한 figure·table을 직접 선택·캡처해 저장하고 해당 방법·실험 설명 중간에 삽입한다. 전체 pipeline, 핵심 비교 결과, 설계 선택을 뒷받침하는 ablation을 우선 검토하며, 캡처의 글씨·축·범례·표 숫자가 읽히는지 확인한다. 구체적인 추출·저장·검수 순서는 Markdown 작성 명세를 따른다.

기본 이미지 경로는 `/assets/img/YYYY-MM-DD-주제/파일명.png`이다. 기존 글의 폴더 날짜가 게시일과 다른 경우가 있으므로 실제 파일 존재 여부를 확인한다. 가능하면 `pipeline`, `stage1`, `main-results` 같은 의미 있는 새 파일명을 사용한다. 기존 screenshot 이름은 자동 변경하지 않는다.

긴 추가 설명에 사용하는 기존 HTML 형식은 다음과 같다.

```html
<details><summary>이 수식은 왜 이렇게 바꿀 수 있는가</summary>
  <div markdown="1">

추가 유도나 비교 설명

  </div>
</details>

<br>
```

접힌 내용에 들어가야만 방법의 핵심을 알 수 있게 만들지 않는다. 상세 증명·비교·질문 답변에 사용한다.

## 코드 사용

코드는 필수 장이 아니다. 수식보다 코드로 설명하기 쉬운 경우에만 작은 의사코드를 넣는다. 논문과 구현의 관계가 중요하거나 사용자가 요청하면 Code 장을 추가한다.

- `논문식/모듈 → 해당 코드 → 연산·shape·순서 → 이유`를 연결한다.
- 공식 구현 링크는 실제 확인한 파일과 commit 또는 안정적인 위치를 기준으로 한다.
- 의사코드와 실행 가능한 코드를 구분한다. 코드를 확인하지 않고 “공식 구현과 동일하다”고 쓰지 않는다.
- 상수나 초기값을 주석으로 설명할 때도 원문과 맞춘다. 예: SigLIP은 `t_prime = log(10)`, `t = 10`을 구분해야 한다.

## Jekyll 작성 형식

### 주제별 디렉토리 선택과 생성

새 포스팅의 저장 위치도 작성 과정에서 직접 정한다. 사용자는 기존 주제별 분류를 활용하고, 적합한 디렉토리가 없으면 새로 만들어 글을 추가하도록 요청했다.

현재 구조는 다음과 같다.

```text
_posts/Paper Reivew/
├── 3D Vision/
├── Audio/
├── Computer Vision/
│   ├── Diffusion/
│   └── GAN/
├── Multimodal/
└── NLP/
```

| 논문의 핵심 대상과 기여 | 기본 저장 위치 |
| --- | --- |
| 3D 표현·재구성·렌더링·3D 생성과 편집 | `3D Vision/` |
| 음성·오디오의 단일 모달 모델링과 생성 | `Audio/` |
| 시각 backbone·표현 학습·모델 해석 등 일반 vision | `Computer Vision/` |
| 기존 Diffusion 글과 같은 계열의 시각 diffusion 방법 | `Computer Vision/Diffusion/` |
| GAN의 원리·구조·학습 및 GAN 기반 시각 변환 | `Computer Vision/GAN/` |
| 모달리티 간 정렬·결합, CLIP/VLM/MLLM, 다중 모달 이해·생성 | `Multimodal/` |
| 언어 모델·텍스트 이해·언어 task 중심의 기반 방법 | `NLP/` |

- 원문을 읽어 핵심 연구 문제와 기여를 기준으로 분류하고 가까운 기존 포스팅의 위치를 함께 참고한다.
- 제목이나 backbone에 `Diffusion`, `Transformer`, `Audio`가 등장한다는 이유만으로 분류를 결정하지 않는다. 예를 들어 Diffusion Bridge·VLV·SD3는 현재 Multimodal에 있고, SplatFlow는 3D Vision, AnyGPT는 Multimodal, WaveNet은 Audio에 있다.
- 여러 분야에 걸치면 글의 중심 설명에 가장 적합한 디렉토리 하나에 저장하고 나머지 관련 주제는 tags에 반영한다. 같은 포스팅을 여러 폴더에 복제하지 않는다.
- 적합한 분류가 기존 구조에 없으면 상위 분야 아래의 새 하위 디렉토리 또는 새로운 분야 디렉토리를 만들어 실제 Markdown을 저장한다. 예를 들어 반복 사용할 새로운 NLP 하위 주제라면 `NLP/새 주제/`를 만들 수 있다. 현재 글을 저장할 필요가 있을 때 생성하며 미리 빈 디렉토리를 늘리지 않는다.
- 기존 `Computer Vision`, `3D Vision`, `Multimodal`, `NLP` 등의 명칭과 표기 관례를 맞춘다. 이미 같은 뜻의 디렉토리가 있는지 먼저 확인한다. 실제 루트명 `Paper Reivew`는 그대로 유지한다.
- 이 분류 판단과 필요한 디렉토리 생성은 포스팅 작성에 포함된 작업이다. 사용자가 논문마다 저장 위치를 지정해줄 것을 전제로 하지 않는다. 사용자가 특정 위치를 지정하면 그 지시를 우선한다.
- 현재 폴더를 참고해 새 글을 분류하는 요청을 기존 포스팅 전체의 이동·재분류 요청으로 확대하지 않는다.
- front matter의 categories와 tags도 새 글의 분야에 맞춘다. 현재 `Multimodal/`의 최근 categories 표기는 `Multi Modal`이고 `Computer Vision/`은 `Computer Vision`이므로 기존 사이트 분류 이름을 활용한다. 폴더 경로를 그대로 categories 문자열로 복사하지 않는다.
- `typora-root-url`은 실제 포스팅 부모 디렉토리에서 저장소 루트까지의 상대 경로를 계산한다. 기본 분야 폴더는 `../../../`, `Computer Vision/Diffusion/`·`Computer Vision/GAN/`처럼 한 단계 더 깊으면 `../../../../`이다. 새 하위 폴더도 깊이에 맞춰 계산한다.
- asset은 포스팅 폴더와 별도로 `assets/img/YYYY-MM-DD-주제/`에 저장한다. Markdown의 사이트 루트 이미지 경로 `/assets/img/...`도 함께 확인한다.

### Front matter와 서지정보

```yaml
---
title: "[Paper Review] 논문 약칭 또는 제목"
date: YYYY-MM-DD HH:MM:SS +0900
categories: [Paper Review, 분야, 확인된학회연도]
tags: [핵심분야, 방법, task]
use_math: true
typora-root-url: ../../../
---
```

```markdown
# **[논문 리뷰] 정확한 영문 논문 제목**

> **정확한 영문 논문 제목**
>
> 저자 이름 et al.
>
> 확인된 학회와 연도 또는 arXiv preprint
>
> [[arXiv](실제논문주소)] [[Github](공식코드주소)] [[Project Page](실제프로젝트주소)]
```

- 파일명은 `YYYY-MM-DD-주제.md`로 한다. 새 파일에서는 파일명 날짜와 front matter 날짜를 일치시킨다.
- 게시 날짜는 현재 사용자 요청과 Asia/Seoul을 기준으로 정한다. 기존 `+/-0000` 표기를 재현하지 않는다.
- front matter의 `use_math`는 실제 boolean `true`다. 설명 문장을 값에 섞지 않는다.
- 학회, 수상, 공개 여부는 확인된 정보만 넣는다. 학회가 미확인이면 비워둔 행 대신 preprint로 표시한다.
- `Paper Reivew`는 현재 실제 폴더명이다. 요청 없이 폴더 전체를 이름 변경하지 않는다.
- `typora-root-url`은 Markdown 파일 위치에 따른 저장소 루트의 상대 경로다. 하위 폴더가 더 깊으면 조정한다.
- 분야와 tags는 이 저장소의 기존 분류와 해당 논문의 실제 주제에 맞춘다. 기존 데이터의 대소문자를 일괄 수정하지 않는다.

## 로컬 렌더링 검증과 최종 확인

사용자가 논문 PDF와 arXiv TeX 압축파일을 제공하면 이 문서의 기준에 따라 원문을 읽고, 포스팅·figure·table asset을 준비하고 주제 디렉토리에 저장한다. PDF와 source의 논문 버전을 맞추고, 수식·그림의 실제 내용을 대조한다. 별도 보충자료가 제공되면 필요한 근거도 확인한다.

글과 assets를 저장한 다음 다음 과정을 완료한다.

1. **로컬 서버 실행**: 저장소 루트 `/Users/ghahn/HahnGyuTak.github.io`에서 사용자가 지정한 `bundle exec jekyll serve`를 실행한다. 서버 시작과 사이트 생성 완료 로그를 확인한다. 같은 저장소의 서버가 이미 실행 중이면 해당 서버의 재생성을 확인해 활용할 수 있다. 다른 작업의 서버를 임의로 종료하지 않는다.
2. **새 글 진입 확인**: 브라우저에서 `http://127.0.0.1:4000/`을 열고 새 글이 목록에 표시되는지 확인한다. 실제 링크를 따라 해당 글의 생성된 URL을 열어 검수한다. 파일명만으로 URL을 추정해 검증을 생략하지 않는다.
3. **본문 전체 확인**: 글의 처음부터 끝까지 실제 렌더링을 확인한다. 소스 문법 검사나 HTTP 200 응답만으로 웹 렌더링 검증을 대체하지 않는다. 클라이언트 수식 처리가 끝난 상태에서 확인한다.
4. **오류 수정과 재확인**: 빌드 오류, Liquid·YAML·Markdown·HTML 오류, 깨진 수식·이미지·표·토글·목록·코드, 가독성을 해치는 배치를 수정한다. 재생성된 최종 수정본을 브라우저에서 다시 확인한다. 현재 글 또는 작성 과정에서 생긴 오류를 우선 수정하고, 기존 사이트 전체의 무관한 문제로 변경 범위를 무작정 확대하지 않는다.
5. **사용자에게 결과 제시**: 오류 수정과 최종 렌더링 검증을 마치면 Markdown 파일 링크, 실제 로컬 글 URL, 확인한 항목과 중요한 내용상의 판단을 간결하게 보여준다. 검증하지 못한 부분이 남아 있으면 그 범위를 밝히고 완전히 확인됐다고 보고하지 않는다.
6. **최종 컨펌과 푸시**: 사용자가 글을 읽고 수정을 요청하면 반영하고 렌더링을 다시 확인한다. 사용자가 최종 확인 후 GitHub 푸시를 명시적으로 승인할 때만 푸시한다. 승인 전에 원격 저장소에 올리거나 공개 사이트에 배포하지 않는다. 로컬 작성·서버 실행·검증은 이미 요청된 작업으로 진행한다.

### 브라우저에서 확인할 항목

- 홈 또는 게시물 목록에 새 글이 표시되고 실제 글 링크가 열린다.
- 게시물 제목·서지 인용문·H2/H3 목차·본문의 순서와 계층이 맞는다.
- `$...$`와 `$$...$$`가 의도한 수식으로 표시된다. raw delimiter·LaTeX 명령·수식 오류 문구가 남거나 식이 중복 렌더링되지 않는다.
- 식 번호, 긴 aligned 식, 수식 아래 기호 bullet이 읽히고 폭 때문에 가려지지 않는다.
- 모든 figure·table 이미지가 로드되고, crop·글씨·축·범례·숫자가 본문 크기에서 읽힌다.
- HTML `<details>`를 실제로 열고 닫을 수 있으며, 열린 내부의 목록·표·코드·수식도 정상이다. 처음에 접혀 있다는 이유로 내부 검수를 생략하지 않는다.
- nested quote, 번호 목록과 하위 bullet, 이미지와 보충 문단이 의도한 항목 안에 표시된다.
- Markdown 비교 표, 코드 fence와 강조·링크가 정상이며 HTML 소스가 본문에 그대로 노출되지 않는다.
- 내부 링크·asset 요청에 404가 없고 현재 글과 관련된 브라우저 오류가 없다. 외부 논문·코드 링크는 올바른 출처를 가리킨다.
- 일반 화면과 좁은 화면에서 긴 수식·표·가로 이미지가 본문을 읽기 어렵게 만들지 않는다.

환경이나 의존성, 외부 수식 스크립트 로딩 문제로 검증할 수 없으면 원인을 확인하고 가능한 범위에서 해결한다. `bundle exec jekyll serve`가 실행됐다는 사실과 실제 글의 렌더링 검증이 끝났다는 사실을 구분한다. 미리보기를 보여줄 때는 해당 서버가 계속 접근 가능한 상태인지 확인하고, 로컬 서버 실행을 공개 배포로 설명하지 않는다.

## 작성 전후 확인 목록

- [ ] 핵심 주제와 유사한 기존 글을 기준으로 저장 디렉토리를 선택했고, 없으면 적합한 디렉토리를 생성했다.
- [ ] categories·tags와 실제 경로 깊이에 맞는 typora-root-url을 확인했다.
- [ ] 논문 링크의 제목·저자·버전이 대상과 일치하고 본문을 읽었다.
- [ ] 필요한 supplementary 근거와 관련 연구의 1차 출처를 확인했다.
- [ ] 목표·기존 실패·novelty가 연결되고, 일반 배경과 새 기여가 구별된다.
- [ ] 핵심 모듈마다 입력·출력·역할·연산과 설계 이유가 설명된다.
- [ ] 학습과 추론, paired/unpaired 데이터, trainable/frozen 모듈을 구분한다.
- [ ] 수식의 기호·차원·부호·초기값·평균화 기준과 유도 단계를 확인했다.
- [ ] 실험마다 질문·조건·지표·결과·해석이 있고 예외를 숨기지 않았다.
- [ ] 모델 크기 M/B, 억 단위, token/문자, %, percentage point, AUC/accuracy를 혼동하지 않았다.
- [ ] 원문 주장, 글의 해설, 가설·개인 판단의 경계가 보인다.
- [ ] 그림의 패널·색·축·표 번호가 설명과 맞고 로컬 경로가 존재한다.
- [ ] H1·서지 quote·H2 흐름·H3 설명 단위·수식 아래 기호 bullet·긴 부연 토글이 Markdown 작성 명세와 맞다.
- [ ] 코드·HTML·수식 delimiter, 들여쓰기·빈 줄과 front matter가 유효하다.
- [ ] 날짜·서지 제목·학회·공식 링크에 이전 글의 복사 잔재가 없다.
- [ ] 사용자가 주지 않은 개인 경험·감상을 작성하지 않았다.
- [ ] 다시 읽었을 때 이 방법을 자기 말로 설명할 수 있는 글이다.
- [ ] `bundle exec jekyll serve`로 최종 소스가 생성됐고 홈과 실제 글 페이지를 브라우저에서 확인했다.
- [ ] 본문 전체와 열린 토글 안의 수식·이미지·표·코드·목록·레이아웃을 확인하고 오류 수정 후 다시 검수했다.
- [ ] Markdown 파일과 실제 로컬 글 URL을 사용자에게 제시했으며 GitHub 푸시는 최종 명시적 승인 전까지 수행하지 않았다.

일정 분량을 맞추거나 모든 절에 같은 설명을 채우는 것이 목표가 아니다. 핵심을 빠뜨리지 않으면서 이해에 필요한 깊이를 확보한다.
